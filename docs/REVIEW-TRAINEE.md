## M00 — 오리엔테이션

교재대로 접속하고, `lab-whereami` 를 읽고, 서비스망을 죽여 보고, 검증까지 통과했다
(4/4). 퀴즈 5문항은 전부 README 안에서 답이 나온다.

### M00-1 · 걸림돌 — 실습 4 를 하면 "설정이 안 올라갔다" 고 한다

실습 4 는 `sudo ip link set eth1 down` 을 시킨다. 그러고 `lab-whereami` 를 치면:

```
eth1       down     -                    sw1            access [VLAN 10]

이 노드에 아직 주소가 없습니다 — 설정이 안 올라간 상태입니다.
웹 콘솔에서 [이 모듈 적용] 을 누르면 올라갑니다 (1분쯤).
```

그리고 바로 위 실습 4 의 주의는 이렇게 적혀 있다 —
"`lab-whereami` 가 '설정이 안 올라간 상태입니다' 라고 하면 먼저 적용하고 오세요."

시킨 대로 한 사람이 **시킨 대로 하지 말라는 안내를 받는다.** 그대로 따르면
[이 모듈 적용] 이 실습 4 를 되돌려 버려서 한 바퀴를 헛돈다.

원인 — `lab-whereami.j2` 는 주소가 없으면 무조건 `missing=1` 로 본다.
링크가 내려가 있어서 주소가 안 보이는 것과 설정이 안 올라간 것을 구분하지 않는다.

> 고칠 것 — 링크가 `up` 인데 주소가 없을 때만 그 문구를 낸다.
> 링크가 `down` 이면 "링크가 내려가 있습니다" 로 말한다.

### M00-2 · 걸림돌 — 본문 두 곳이 평서형인데 `make style` 이 못 잡는다

`README.md.j2:65` `…관리 포트(mgmt0 · me0 · management)다.`
`README.md.j2:166` `…ssh 에게 알려 주는 것이다(ProxyJump).`

둘 다 도입부가 아니라 본문이라 존댓말이어야 한다 (STYLE 1). `make style` 의
평서형 칸은 m00 을 `0` 으로 센다. 검사기가 두 군데서 샌다:

- `PLAIN` 은 `다` 앞에 한글이 있어야 잡는다. `…)다.` 처럼 괄호가 바로 앞이면 못 잡는다
- `PAREN` 의 따옴표 가드는 **줄 단위**로 큰따옴표를 센다. 인용이 두 줄에 걸치면
  뒷줄만 홀수로 세어져 멀쩡한 문장을 인용으로 오인하고 건너뛴다

### M00-3 · 걸림돌 — `dist/modules` 에 없어진 모듈이 남는다

`make docs` 는 출력 디렉토리를 비우지 않는다. 예전 번호로 만든 폴더가 그대로 남아
지금 `dist/modules` 에는 18개가 있다 (실제 모듈은 12개).

```
m05-ipv6  m06-transport  m07-packet-analysis  m08-application
m09-nat-firewall  m10-troubleshooting        ← 전부 옛 번호
```

관리자가 `dist/` 를 통째로 교육생에게 주면 **같은 내용의 M5 가 두 개** 간다.

## M01 — L1/L2 와 스위칭

실습 1~4 는 교재의 출력과 **그대로** 맞았다. 특히 실습 4(플러딩 증명)는 r1 에
`52:54:00:de:ad:01` 앞으로 가는 프레임이 그대로 잡혔다 — 교재가 약속한 증거가
실제로 나온다.

### M01-1 · 어긋남 — 교재가 "[복구] 로 되돌리라" 고 하는데 그러면 실습이 인정되지 않는다

교재 §5: `다 찾았으면 [복구] 로 되돌립니다.`
과제 4-④: `[복구] 로 되돌립니다. 엉켰으면 [이 모듈 적용] 이 확실합니다`
그런데 같은 과제 파일 아래 「어떻게 제출하나」:

> 주의 — 장애 실습은 **[복구]** 나 **[이 모듈 적용]** 으로 되돌리면 인정되지 않습니다.

콘솔이 실제로 그렇게 판정한다 (`app.py:drill_verdict` — `broken` 이 비어 있으면
아무것도 세지 않는다). 즉 **교재가 시키는 대로 하면 통과가 안 된다.**

교재가 9개 모듈에서, 과제가 8개 모듈에서 같은 문장을 쓴다.

| 자리 | 모듈 |
|---|---|
| README §5 `다 찾았으면 [복구] 로 되돌립니다` | m01 m02 m03 m04 m06 m07 m08 m09 m10 |
| tasks 과제 `④ [복구] 로 되돌립니다` | m01 m02 m04 m05 m06 m08 m09 m10 |

> 고칠 것 — 순서를 뒤집는다. **손으로 고치고 [검증] 을 돌린다**가 먼저고,
> [복구] 는 포기하거나 엉켰을 때의 길이다.

### M01-2 · 어긋남 — 모든 모듈이 "틀린 문항은 그 자리에서 해설이 나옵니다" 라고 한다

12개 모듈 전부 마지막 줄이 이렇다. 실제 콘솔은 **해설을 안 준다** — 어느 문항을
틀렸는지와 자기가 고른 답만 보여 준다 (`assess.py:234`, `_result.html:49`,
`docs/DECISIONS.md` 6번에 그렇게 정하신 내용). `_module.html:89` 는 바르게
적혀 있어서, 같은 화면 안에서 교재와 콘솔이 서로 다른 말을 한다.

### M01-3 · (취소) — 내가 잘못 본 것이었다

처음에 "실습 3 의 MAC 테이블에 `vlan 10` 이 섞여 나온다" 고 적었는데, 그것은 랩을
m7 에서 m1 으로 **내려온** 탓이었다. 신규 랩에서는 교재대로 두 줄만 나온다.
남는 문제는 「되돌리기가 한 방향으로만 수렴한다」 쪽으로 옮겨 적었다.

### M01-4 · 걸림돌 — 실습 5(에이징)가 교재대로 안 보인다

`ageing_time 1500`(15초) 로 낮추고 한 번 통신한 뒤 지켜본 실제 값:

```
t=0s   used 0/0
t=7s   used 2/2      ← 5초쯤에 무언가 갱신했다
t=14s  used 9/9
```

pc1·pc2 의 이웃 캐시가 주기적으로 서로에게 ARP 를 다시 던진다(실습 2 캡처의
마지막 두 줄이 그것이다). 그 ARP 가 fdb 를 계속 되살려서 **15초가 지나도 항목이
안 사라진다.** 과제 2 는 `20초 후 (항목이 사라졌는가)` 를 그대로 적으라고 한다.

> 고칠 것 — 교재가 이 되살림을 먼저 말해 주고
> (`ip neigh flush` 를 양쪽에서 먼저 하라거나), 관찰 시간을 늘려야 한다.

## M02 — IP 주소와 L3

3절(직접 만들기) 을 교재 그대로 손으로 따라가 **9/9 통과**했다. 6.2(목적지 MAC 이
바뀌는 순간)는 트렁크와 액세스 양쪽 캡처가 교재의 표와 정확히 같았고,
6.5(브로드캐스트가 VLAN 을 못 넘는다)도 pc2 캡처가 한 줄도 안 올라오는 것까지
그대로였다. m02-04 장애도 증상·힌트가 맞고 손으로 고쳐 통과했다.

### M02-1 · 막힘 — 6.4 ④⑤ 는 성공과 실패가 화면에서 구분되지 않는다

교재는 블랙홀을 만든 뒤 "멈춥니다", MSS clamp 뒤에는 "이번에는 갑니다" 라고 한다.
판단 근거로 준 것은 `; echo "종료 코드 = $?"` 하나다. 실제로 돌려 보면:

| | 걸린 시간 | 종료 코드 | 실제로 도착한 바이트 |
|---|---|---|---|
| 블랙홀 (실패) | 10.0초 | **0** | **0** |
| MSS clamp (성공) | 10.0초 | **0** | 3145728 |

`nc -w 10` 이 어느 쪽이든 10초 뒤에 0 으로 끝난다. **교육생 화면에서는 두 경우가
똑같이 보인다.** 성공했는지 실패했는지 알 방법이 교재 안에 없다.

> 고칠 것 — 받는 쪽을 `nc -l 9000 | wc -c` 로 바꾼다. `0` 과 `3145728` 로 갈린다.
> 보내는 쪽의 `종료 코드` 안내는 아무것도 말해 주지 않으므로 뺀다.

### M02-2 · 어긋남 — `systemctl restart lab-switch` 로는 초기 구성으로 안 돌아간다

3.0 의 되돌리기 표가 이렇게 약속한다.

| `sudo systemctl restart lab-switch` (`sw1`) | 스위치 포트와 VLAN 이 초기 구성으로 |

직접 해 봤다. `eth1` 에 `vid 10 pvid` 를 심어 두고 재시작:

```
--- 재시작 뒤 ---
port              vlan-id
eth1              10 PVID Egress Untagged      ← 그대로 남았다
```

`lab-switch-up.sh` 는 VLAN 을 **더하기만** 한다. `vlan_filtering` 이 꺼지는 단계에서는
`bridge vlan del` 줄이 통째로 `{% raw %}{% if vf %}{% endraw %}` 안에 있어 실행되지도 않는다.
[이 모듈 적용] 은 `reset.yml` 이 브리지를 통째로 지우므로 제대로 돌아간다 —
**둘 중 교재가 권하는 가벼운 쪽만 안 듣는다.**

> 고칠 것 — 스크립트가 브리지를 지우고 다시 만들게 한다 (수렴하는 스크립트로).

### M02-3 · 걸림돌 — 3.1 과 3.2 의 `bridge vlan show` 출력이 실제와 다르다

3.2 를 마친 뒤 교재는 이렇게 나온다고 한다.

```
eth1              10 PVID Untagged
eth2              20 PVID Untagged
eth3              1 PVID Untagged      ← 실제로는 이 줄이 없다
```

`vlan_default_pvid 0` 을 주는 순간 손대지 않은 `eth3` 의 `vid 1` 까지 사라진다.
그리고 실제 출력은 `PVID Egress Untagged` 다 (커널이 `Egress` 를 함께 찍는다).
교재의 세 곳(3.1 · 3.2 · 3.4)이 모두 `Egress` 없는 옛 표기다.

### M02-4 · 걸림돌 — `FAILED` 라고 했는데 `INCOMPLETE` 로 보인다

3.2 의 결정적 증거가 `ip neigh` 의 `FAILED` 인데, ping 을 돌리는 중에는 계속
`INCOMPLETE` 로 보인다. 퀴즈 q2 도 `FAILED` 를 전제로 낸다. M1 은 두 상태를
같이 설명해 두었으니 M2 도 한 줄이면 된다.

### M02-5 · 걸림돌 — 캡처마다 `ICMP net 10.10.40.13 unreachable` 이 섞인다

노드의 `/etc/resolv.conf` 가 처음부터 `nameserver 10.10.40.13` 을 가리킨다.
그 서버는 **M9 에서야 선다.** 그때까지 노드에 SSH 로 붙을 때마다 sshd 의 역조회가
그 주소로 나가고, r1 이 `net unreachable` 을 돌려준다. 6.2 처럼 `-e -n icmp` 로
거는 캡처에는 이 잡음이 진짜 프레임보다 많이 잡힌다 (내 캡처는 8줄 중 6줄이 잡음).

> 고칠 것 — 잡음을 교재가 미리 알려 주거나, DNS 가 서기 전 단계에서는
> `resolv.conf` 를 비워 둔다.

## M03 — 정적 라우팅

3절을 손으로 다 만들어 **9/9 통과**했다. 6.4(리턴 경로 삭제)의 세 줄 캡처,
6.5(`* * *`), 6.6(floating static)은 교재 그대로 나왔다. traceroute 홉 주소도
교재의 예상과 일치한다.

### M03-1 · 막힘 — 3.2 의 "패킷이 한 홉 더 갔다는 증거" 가 실제로는 안 나온다

교재 3.2:

> **여전히 안 됩니다.** 그런데 아까와 답이 다릅니다. `Destination Net Unreachable` 이
> `r1` 이 아니라 `10.10.64.2`(`r2`)에서 옵니다. **패킷이 한 홉 더 갔다는 증거입니다.**

실제로 돌린 결과 — 아무 답도 오지 않는다.

```
$ ping -c 3 -W 2 10.10.40.11
PING 10.10.40.11 (10.10.40.11) 56(84) bytes of data.

--- 10.10.40.11 ping statistics ---
3 packets transmitted, 0 received, 100% packet loss
```

r1–r2 링크를 떠 보면 요청은 r2 까지 가고, **r2 는 아무것도 돌려보내지 않는다.**

```
IP 10.10.10.11 > 10.10.40.11: ICMP echo request, seq 1
IP 10.10.10.11 > 10.10.40.11: ICMP echo request, seq 2
(끝)
```

당연한 결과다 — r2 는 `10.10.10.11` 로 가는 경로가 없으니 **그 오류를 보낼 수가 없다.**
3.3 에서 배우는 바로 그 이야기(리턴 경로가 없으면 오류도 못 돌아온다)가
3.2 에서 이미 일어나 버린다.

이게 M3 에서 가장 큰 문제인 이유는 **과제 1(★)이 이 장면 위에 통째로 서 있기** 때문이다.

| 단계 | 넣은 줄 | 결과 (문구 그대로) | **누가** 그 답을 보냈나 |
|---|---|---|---|
| 3.2 | `r1` 한 줄 | ← 적을 것이 없다 | ← 아무도 안 보냈다 |

그리고 이어지는 질문 — "3.1 과 3.2 는 문구가 같은데 **보낸 사람이 다릅니다.** 그것이
무엇을 알려 주는가" — 는 답이 없는 질문이 된다. 퀴즈 q1 도 같은 전제로 낸다.

> 고칠 것 — 셋 중 하나.
> ① 3.2 를 "이번에는 오류조차 오지 않는다" 로 고치고, 그 이유(r2 에 리턴 경로가
>    없다)를 3.3 의 예고편으로 쓴다. 과제 1 · 퀴즈 q1 도 같이 고친다.
> ② r1–r2 구간을 진단할 수 있게 `r2` 에 Site-A 리턴 경로만 미리 넣어 둔 상태로
>    시작한다 (그러면 교재의 문장이 사실이 된다).
> ③ 3.2 확인을 `r2` 에서 캡처하는 것으로 바꾼다 — 어차피 M3 의 교훈이 그것이다.

### M03-2 · 걸림돌 — 3.1 의 `show ip route` 에 없는 줄이 실제로는 둘 더 있다

교재는 세 줄만 보여 준다. 실제로는 다섯 줄이다.

```
C>* 10.10.96.1/32 is directly connected, lo0      ← 교재에 없음. 설명도 없음
C>* 172.30.1.0/24 is directly connected, mgmt0    ← 교재에 없음
```

`10.10.96.1/32` 는 M4 의 OSPF router-id 로 쓸 루프백인데, M3 시점에는 어디에도
설명이 없다. 처음 라우팅 테이블을 읽는 자리에서 모르는 줄이 둘 나온다.

### M03-3 · 막힘 — `m01-02` 의 [복구] 가 랩을 되돌리지 못한다 (중간 점검이 걸린다)

중간 점검(cp1)이 뽑는 7개 장애를 하나씩 넣고 판정을 돌려 봤다. 판정은 7개 다
잡아냈다 — 그런데 **두 번째부터 랩이 계속 깨진 채로 남았다.**

```
m01-01  →  18/20   (정상)
m01-02  →  17/20
m01-03  →  16/20   ← 여기부터 M02 · pc1 → pc2 가 계속 실패로 남는다
...
m03-04  →  15/20
```

원인은 `scenarios/m01-02.yml` 이다. 넣을 때는 `ip link set eth2 nomaster`,
되돌릴 때는 `ip link set eth2 master br0` **한 줄뿐**이다.

M1 단계는 `vlan_filtering 0` 이라 이걸로 충분하다. 그런데 **M2 부터는
`vlan_filtering 1` 이고 `vlan_default_pvid 0`** 이라, 브리지에서 뺐다 다시 꽂은
포트는 **VLAN 을 하나도 못 받는다.**

```
port              vlan-id
eth1              10 PVID Egress Untagged
eth3              10 / 20 / 999 PVID
                                        ← eth2 가 아예 없다. pc2 는 고립된 채로 남는다
```

`sudo bridge vlan add dev eth2 vid 20 pvid untagged` 를 손으로 넣어야 돌아온다.

**왜 이게 심각한가** — `m01-02` 는 **중간 점검 cp1 의 pool 에 들어 있고**, cp1 은
`m3` 단계에서 돈다. 그 회차를 뽑은 교육생은

- 원인을 정확히 찾아 `ip link set eth2 master br0` 로 고쳐도 통신이 안 돌아오고
- [포기 - 정답 확인] 을 눌러도 안 돌아오고
- [결과 확인] 은 계속 떨어진다

[이 모듈 적용] 말고는 빠져나갈 길이 없다. 게다가 M1 에서 같은 장애를 연습할 때는
잘 되던 것이라 "내가 뭘 잘못했나" 를 한참 찾게 된다.

> 고칠 것 — `fix` 에서 VLAN 까지 되돌린다. `m01-02` 뿐 아니라 브리지 멤버십을
> 건드리는 시나리오 전부를 같은 눈으로 봐야 한다.

## M04 — OSPF

네 대를 한 대씩 켜서 **11/11 통과**했다. 3.2 의 "오류 대신 머리글만 찍히는 화면",
3.3 의 첫 인접, 3.5 의 이웃 2개는 교재 그대로다.

### M04-1 · 어긋남 — 퀴즈 q9 와 과제 1 이 교재 3.7 과 정반대를 말한다

교재 3.7:

> 정적이 남아 있는 지금, 서버로 가는 길은 **이미 OSPF 를 타고 있습니다.**
> … 더 긴 쪽이 이깁니다. **정적을 남겨 두면 OSPF 가 안 쓰인다는 말은 이 랩에서는 맞지 않습니다.**

퀴즈 q9:

> 3.7 에서 정적 경로를 걷어내기 **전에는** … `pc1` → `web` 트래픽이 계속 **정적 경로로** 갔습니다. 왜인가?
> 정답 ▸ 정적 경로(AD 1)가 OSPF(AD 110)를 이기기 때문입니다

과제 1 의 마지막 물음도 같다 — "3.5 까지 끝났는데도 `pc1` → `web` 은 여전히 **정적 경로**로
갔습니다. 왜인가".

정적을 걷어내기 직전에 실제로 확인했다.

```
r1# show ip route 10.10.40.11
Routing entry for 10.10.40.0/24
  Known via "ospf", distance 110, metric 21, best      ← OSPF 다
  * 10.10.64.2, via eth2, weight 1
```

**교재가 맞고 퀴즈·과제가 틀렸다.** 퀴즈는 100점이 통과 기준이라, 교재를 제대로
읽은 사람일수록 여기서 막힌다 — 그리고 어느 보기도 정답이 아니다.

### M04-2 · 걸림돌 — 3.5 의 `show ip route ospf` 예시 한 줄이 실제와 다르다

교재:

```
O>* 10.10.64.12/30 [110/200] via 10.10.64.6, eth3, weight 1
```

실제:

```
O>* 10.10.64.12/30 [110/120] via 10.10.64.2, eth2, weight 1
```

r3–r4 링크로 가는 길도 **r2 를 도는 편이 싸다** (10+10+100=120 < 100+100=200).
교재는 백업 경로 쪽으로 간다고 적어 두었다.

### M04-3 · 걸림돌 — 마지막 줄이 다음 모듈을 M6 라고 한다

`README.md.j2:1495`

> [검증]까지 통과하면 다음 모듈이 열린다 — **M6. IPv6.**

M4 다음은 **M5(게이트웨이 이중화)** 다. (과제 쪽 "M5 로 넘어가도 됩니다" 는 맞다.)
같은 줄이 평서형이기도 하다.

### M04-4 · 어긋남 — 6.1 · 6.3 에서 패킷이 하나도 안 빠진다

교재 6.1 은 `ping -i 0.2` 를 돌린 채 `r1` 의 `eth2` 를 내리고

> 142 와 143 이 없습니다. 그 두 개가 수렴 시간입니다.

라고 한다. 관찰 포인트 표도 "링크 다운은 1~2개" 다. 실제로 재 봤다.

| 무엇 | 도착 | 빠진 구간 | 경로 |
|---|---|---|---|
| 6.1 `r1` 의 `eth2` down (내 쪽) | 125/125 | **없음** | `10.10.64.2` → `10.10.64.6` 으로 바뀜 |
| 6.3 `r2` 의 `eth1` down (상대 쪽) | 125/125 | **없음** | 〃 |

경로는 확실히 바뀌었다 (끊은 직후 traceroute 2번 홉이 `10.10.64.6`). 다만 수렴이
200ms 보다 빨라서 `-i 0.2` 로는 한 개도 못 잡는다.

과제 3 은 이 숫자를 표에 적고 **1번과 2번을 비교**하게 한다. 실제로는 둘 다 0 이라
비교가 성립하지 않는다. (인접이 40초 동안 `Full` 로 남는 것은 그대로 관찰된다 —
차이를 보여 주는 자리는 패킷 수가 아니라 `show ip ospf neighbor` 쪽이다.)

> 고칠 것 — 간격을 `-i 0.05` 로 줄이거나, "환경에 따라 한 개도 안 빠질 수 있다"
> 를 적고 과제의 비교 축을 **감지 방식**(carrier 즉시 vs Dead timer)으로 옮긴다.

## M05 — 게이트웨이 이중화 (VRRP)

3절을 손으로 다 만들어 **10/10 통과**했다. 마지막에 `pc1` 이 보는 게이트웨이 MAC 이
`00:00:5e:00:01:0a` 로 바뀌는 것까지 교재 그대로다. 다만 **3.2 를 교재대로 치면
아무 일도 일어나지 않는다.**

### M05-1 · 막힘 — 3.2 의 명령이 주소를 바꾸지 못한다

교재 3.2 (할 일 ① — 이 모듈의 첫 단계):

```
r1(config-if)# no ip address 10.10.10.254/24
r1(config-if)# ip address 10.10.10.252/24
```

이대로 치면 이렇게 된다.

```
eth1.10@eth1     UP    10.10.10.254/24 10.10.10.252/24
                       ↑ 안 지워졌다   ↑ 하나 더 붙었다
```

이유 — `10.10.10.254` 는 **netplan 이 올린 주소**다. FRR(zebra)은 자기가 넣은 주소만
지운다. 그래서 `no ip address` 는 조용히 아무것도 안 하고, `ip address` 는 두 번째
주소를 더한다. 오류도 안 난다.

직접 확인한 것 —

```
[FRR 로 넣은 .252 는 no ip address 로 지워진다]      → 지워짐
[netplan 이 넣은 .254 는 no ip address 로 안 지워진다] → 그대로
```

**결과가 이 모듈의 전제를 깬다.** 할 일 ① 은 "그 주소를 실주소로 가진 장비가 없게
만드는 것" 인데, r1 이 계속 갖고 있다. 그 상태로 3.4·3.5 를 마치면 r1 의 부모
포트가 가상 IP 를 실주소로 들고 ARP 에 답한다 — 교재 **5.2 가 설명하는 바로 그 고장**
상태로 완성된다. 그리고 3.2 의 "**끊겼습니다**" 도 안 일어나므로, 교육생은
"통신이 되는데?" 하고 다음으로 넘어간다.

되는 방법은 리눅스 쪽이다 (3.3 · 3.4 는 이미 그렇게 하고 있다).

```bash
# r1
sudo ip addr del 10.10.10.254/24 dev eth1.10
sudo ip addr add 10.10.10.252/24 dev eth1.10
```

이렇게 하면 교재가 약속한 화면이 그대로 나온다 (통신 끊김 · `ip neigh` 가 못 찾음).

> 고칠 것 — 3.2 를 `ip addr del/add` 로 바꾼다. 3.3·3.4 와 결도 맞는다.
> vtysh 로 남기려면 왜 안 되는지를 함께 적어야 한다 (그 자체로 좋은 교재감이다).

### M05-2 · 걸림돌 — `Master Down Interval` 이 교재 값과 다르다

교재 2.5 는 r1(우선순위 150)의 Master Down Interval 을 **3.41초**로 계산하고,
3.5 의 `show vrrp` 예시도 `3410 ms` 로 적어 두었다. 실제로는 r1·r3 **둘 다** 이렇게 나온다.

```
 Master Down Interval (v4)               3600 ms
```

퀴즈 q4 는 r3(100) 기준 **약 3.6초**를 정답으로 하고 있어 그쪽은 맞다.
화면과 교재가 어긋나는 곳은 2.5 의 계산 예시와 3.5 의 출력 예시다.

### M05-3 · 걸림돌 — VLAN 20 쪽 가상 MAC 인터페이스 이름을 안 알려 준다

3.4 는 VLAN 10 명령만 주고 "VLAN 20 도 같은 방식으로 만듭니다" 로 끝난다.
이름 규칙이 `<부모>-<VRID>` 라 `eth1.20-20` 인데, 표에는 "이름 `...-10`" 으로만
적혀 있어 `eth1.20-10` 으로 만들기 쉽다. 그러면 FRR 이 짝을 못 찾는다.
이 모듈에서 명령을 안 주는 자리가 여기 하나뿐이라 더 눈에 띈다.

### M05-4 · 막힘 — 교재대로 만들면 **페일오버가 안 된다** (3.3 에 OSPF 가 빠졌다)

이 모듈의 중심 실습(6.1 · 4.2 · 과제 2 ★★)이 교재대로 만든 랩에서는 성립하지 않는다.

`r1` 의 `eth1.10` 을 내렸을 때 —

```
100 packets transmitted, 25 received, 75% packet loss
```

교재 6.1 은 `83 received, 17% packet loss` 라고 한다. 실제로는 **끝까지 안 돌아온다.**
`r1` 을 다시 올릴 때까지 계속 죽어 있었다.

VRRP 자체는 정상이다. 넘어가기는 넘어간다.

```
r3#  Virtual Router ID 10 / Status (v4)  Master     ← 자리는 제대로 넘어갔다
pc1$ ping 10.10.10.254  → 0% packet loss             ← 게이트웨이도 산다
```

끊긴 것은 **돌아오는 길**이다.

```
r4# show ip route 10.10.10.11
(한 줄도 안 나온다)
```

`10.10.10.0/24` 을 OSPF 에 광고하던 것은 `r1` 의 `eth1.10`(passive) 하나뿐이었다.
그 포트가 내려가자 대역이 라우팅 도메인에서 통째로 사라진다. 교재 3.3 은 `r3` 에
서브인터페이스와 주소만 만들고 **OSPF 에는 넣지 않는다.** 1.4 의 「할 일 네 가지」
에도 그 항목이 없다.

랩이 기계로 올리는 정답 구성에는 들어 있다 — `design/routing.yml`:

```yaml
  passive_interfaces:
    r1: [eth1.10, eth1.20]
    r3: [eth3.10, eth3.20]        # M5 에서 붙는 백업 게이트웨이 쪽. 여기도 사용자망이다
```

**즉 교재의 3장만 정답 구성과 다르다.** 빠진 두 줄을 넣어 봤다.

```
r3(config)# interface eth3.10
r3(config-if)# ip ospf area 0.0.0.0
r3(config-if)# ip ospf passive
```

넣자마자 —

```
r4# show ip route 10.10.10.11
Routing entry for 10.10.10.0/24
  Known via "ospf", distance 110, metric 101, best
  * 10.10.64.13, via eth2

6.1 다시 측정 → 100 packets transmitted, 85 received, 15% packet loss
```

**교재의 `17%` 와 맞는 숫자가 그때서야 나온다.** 6.1 의 수치는 정답 구성에서 잰
것이고, 3장을 따라 만든 랩에서는 나올 수 없는 값이었다.

**[검증]은 이걸 못 잡는다.** 10/10 통과다. `backup-has-address` 는 주소만 보고,
어느 검사도 "백업 게이트웨이가 그 대역을 광고하는가" 를 묻지 않는다.

> 고칠 것 —
> ① 3.3 에 OSPF 두 줄을 넣고, 1.4 의 할 일을 다섯 가지로 늘린다
> ② 검사에 `r3 가 사용자망을 OSPF 로 광고하는가` 를 더한다 (없으면 같은 일이 또 새어 나간다)
> ③ 이 사실 자체가 좋은 교재감이다 — "첫 홉만 이중화하고 광고를 안 하면 절반만 이중화된 것"

## M06 — IPv6

3절을 손으로 다 만들어 **9/9 통과**했다. 6.3(NDP 캡처)·6.4(`ff02::1`)·6.6(SLAAC)은
교재 그대로 나온다.

### M06-1 · 어긋남 — 3.5 에 `ipv6 ospf6 network point-to-point` 가 빠졌다

M4 의 3.2 는 라우터 간 링크마다 `ip ospf network point-to-point` 를 반드시 넣게 하고,
2.6 에서 왜 그런지도 설명한다. M6 의 3.5 에는 그 줄이 없다. 그대로 따라 하면 —

```
Neighbor ID     Pri    DeadTime    State/IfState         Duration I/F[State]
10.10.96.2        1    00:00:38   Twoway/DROther         00:00:21 eth2[Waiting]
```

`Waiting` 으로 40초를 보내고, 그 뒤에도 이렇게 남는다.

```
10.10.96.2        1    00:00:30     Full/DR              00:00:09 eth2[BDR]
```

교재 6.5 가 보여 주는 화면은 이것이다.

```
10.10.96.2         1  00:00:34  Full/PointToPoint  00:12:03  eth2
```

랩이 기계로 올리는 정답 구성에는 그 줄이 있다 (`frr.conf.j2` 의
`ipv6 ospf6 network point-to-point`). **3장만 빠져 있다.**

통신은 결국 되지만 (검사도 통과한다) 두 가지가 어긋난다 —
① 인접이 서기까지 40초를 기다린다. "안 서는 건가?" 하고 되돌리기 딱 좋은 시간이다
② M4 에서 배운 `Full/-` · `Full/DR` 구분이 IPv6 에서는 반대로 나타난다

### M06-2 · 걸림돌 — 6.3 의 첫 줄이 문장이 아니다

## M07 — 전송 계층

## 여러 모듈에 걸친 것 — 되돌리기가 한 방향으로만 수렴한다

앞 단계로 내려가는 [이 모듈 적용] 이 **올릴 때 한 것을 안 내린다.** 지금까지 세 곳에서
같은 모양을 봤다.

| 무엇 | 올릴 때 | 내릴 때 | 남는 결과 |
|---|---|---|---|
| `sw1` 의 VLAN | `bridge vlan add` | 지우는 명령이 `{% raw %}{% if vf %}{% endraw %}` 안에 있어 안 돎 | 앞 단계 VLAN 이 그대로 (M02-2) |
| `/etc/resolv.conf` | M9 이상에서만 씀 | 지우지 않음 | M2~M8 에서 없어야 할 파일이 남음 |
| `systemd-resolved` | M9 이상에서 중지 | 다시 켜지 않음 | 내려와도 꺼진 채 |

`reset.yml` 이 브리지를 통째로 지우는 덕분에 VLAN 은 **[이 모듈 적용]** 으로는
돌아온다. 하지만 `resolv.conf` 는 그것도 안 된다.

교재가 이것에 걸리는 자리 —

- **M09 3.1** 은 시작 상태를 이렇게 적어 두었다.

  ```
  # pc1
  cat /etc/resolv.conf
  cat: /etc/resolv.conf: No such file or directory
  ```

  M9 이상을 한 번이라도 지난 랩에서는 파일이 그대로 있다. 실제로 지금 m7 단계
  랩에서 이렇게 나온다.

  ```
  search lab.local
  nameserver 10.10.40.13
  ```

- **M2~M8 의 모든 캡처**에 그 서버로 나가는 조회와 `ICMP net unreachable` 이 섞인다
  (M02-5 에 적었다).

> 고칠 것 — 단계가 M9 미만이면 `resolv.conf` 를 지우고 `systemd-resolved` 를
> 되살리는 갈래를 `roles/host` 에 넣는다. 스위치 쪽은 M02-2 와 같은 처방.

## M09 — 응용 계층 (DNS · HTTP · FTP)

교재의 3장을 손으로 다 만들었고 **8/8 통과**했다. 3.2 의 `named-checkzone`,
3.5 의 손으로 쓴 HTTP(`200 OK`)는 교재 그대로다. 다만 시작하기 전에 큰 문제가
둘 있다.

### M09-1 · 막힘 — 시작해 보면 3장이 **이미 다 되어 있다**

M9 의 시작 상태를 교재는 이렇게 적어 두었다.

```
# pc1
cat /etc/resolv.conf
cat: /etc/resolv.conf: No such file or directory

# dns
ss -lunp | grep :53
(아무것도 없습니다)
```

실제로 [이 모듈 적용] 을 누르고 본 것 —

```
search lab.local
nameserver 10.10.40.13            ← 있다
UNCONN  10.10.40.13:53            ← 이미 듣고 있다
dig +short @10.10.40.13 web.lab.local A → 10.10.40.11   ← 이미 답한다
/etc/bind/db.lab.local            ← 존 파일도 있다
vsftpd active, 21번 LISTEN        ← FTP 도 이미 서 있다
```

**만들 것이 하나도 없다.** 이 모듈이 통째로 사라진다.

원인은 위의 「되돌리기가 한 방향으로만 수렴한다」와 같다. `roles/server` 는
`svc_active`(= 그 단계 이상)일 때만 서비스를 **올리고**, 내려갈 때 내리는 갈래가
없다. 이 랩은 예전에 M10 까지 갔던 랩이라 그때 올라간 것이 그대로 남아 있다.

**누가 이걸 겪나** — M9 를 다시 해 보는 사람, 캡스톤(M11)을 한 번 돌린 뒤 앞으로
돌아온 사람, 그리고 **한 번 쓴 랩을 다음 기수에 물려주는 경우** 전부.

확인을 위해 서비스와 파일을 지워 신규 랩 상태로 만든 뒤 교재를 따라가 봤다.
**그때는 교재가 정확히 맞는다** — `No such file or directory` 도, `connection refused`
도, `named-checkzone ... OK` 도 그대로 나온다. 교재가 아니라 되돌리기가 문제다.

### M09-2 · 막힘 — 교재대로 만들면 FTP 검사를 통과할 수 없다

3.4 는 `/etc/vsftpd.conf` 만 만들게 한다. 그런데 —

- 3.4 의 확인 명령 `curl -sS -m 5 ftp://ftp.lab.local/` 은 **`curl: (67) Access denied: 530`** 을 낸다.
  익명 접속을 껐는데 계정을 안 줬기 때문이다. 교재는 "접속 자체가 되는지만 봅니다" 라고만 한다.
- 검사 `FTP Passive 모드로 파일을 실제로 받아오는가 ★` 는
  `curl -u ftpuser:labpass ftp://.../hello.txt` 다. 6.5 의 실습도 같은 계정을 쓴다.
- 그 **`ftpuser` 계정과 `/srv/ftp/hello.txt` 를 만드는 곳은 교재 어디에도 없다.**
  `roles/server` 가 M9 이상에서 만든다 — 즉 **교재가 만들라는 것을 다 만들어도
  생기지 않는다.**

파일만 잠시 치우고 확인해 봤다.

```
$ curl -sS -m10 -u ftpuser:labpass ftp://10.10.40.12/hello.txt
curl: (78) The file does not exist
```

지금 이 랩에서 8/8 이 나온 것은 예전 적용 때 만들어진 계정과 파일이 남아 있기
때문이다. **신규 랩에서 교재만 따라간 사람은 이 검사를 통과할 수 없다.**

> 고칠 것 — 3.4 에 계정 만들기와 테스트 파일 만들기를 넣고, 확인 명령에
> `-u ftpuser:labpass` 를 붙인다. 1.5 「만들 때 쓸 값」에 계정·비밀번호를 적는다.

## M10 — NAT 와 방화벽

3장을 손으로 만들어 봤다. 방화벽·SNAT·DNAT 자체는 교재대로 정확히 동작한다
(안에서 밖 `200`, 밖에서 공개 IP `200`, 열지 않은 포트는 조용히 버려짐).
그런데 **교재만 따라가면 3.1 부터 아무것도 안 된다.**

### M10-1 · 막힘 — 3장에 라우팅이 통째로 빠져 있다

교재 3.1 은 이렇게 적어 두었다.

> **요청은 `inet` 까지 도착합니다.** 출발지가 `10.10.10.11` 인 채로 갑니다.

실제로는 Site-A 밖으로 나가지도 못한다.

```
r1#  show ip route 0.0.0.0/0
(한 줄도 없다)
r4#  show ip route 198.51.100.10
(한 줄도 없다)
edge# show running-config → OSPF 인터페이스가 하나도 없다
```

M10 의 **목표 구성**에는 있지만 **시작 구성**에는 없는 것들이다
(`design/routing.yml` 의 `edge_routing_m9`, `frr.conf.j2` 의 `si >= m10`).

| 어디 | 없는 것 |
|---|---|
| `r4` | 기본 경로 → edge, 그리고 `default-information originate` |
| `edge` | 기본 경로 → inet, 사내 대역 → r4 |
| `inet` | 공인 서비스 블록(`203.0.113.8/29`) → edge |

「할 일은 네 가지」(input · forward · SNAT · DNAT) 어디에도 이 얘기가 없다.

세 곳을 손으로 넣고 다시 해 봤다. 그때서야 교재가 말한 화면이 나온다.

```
(넣기 전) inet 캡처 → 0 packets
(넣은 뒤) inet 캡처 → 5 packets, curl 은 5초 뒤 timeout
          = "요청은 도착하는데 응답이 못 온다" — 교재 3.1 이 말한 그것
(SNAT 뒤) pc1 → 198.51.100.10  http 200
(DNAT 뒤) inet → 203.0.113.10  http 200
```

M5 와 같은 모양이다 — **3장이 정답 구성의 일부만 가르친다.**

### M10-2 · 막힘 — 검증에 3장이 만들 수 없는 항목이 있다

교재대로 다 만들고 [검증] 을 돌린 결과 **8/9 불합격**이다.

```
[FAIL] FTP 서버가 밖에 알려 줄 **공개 주소**를 설정하고 있는가
       출력에 '1' 가 없다 (실제: 0)
```

검사는 `grep -c '^pasv_address=' /etc/vsftpd.conf` 다. 그런데

- M9 3.4 가 주는 `vsftpd.conf` 에 `pasv_address` 가 없다
- M10 3장에도 그 줄을 넣으라는 말이 없다
- M10 2.5 는 "**그래서 이 랩의 vsftpd 설정에는 두 줄이 더 있습니다**" 라고,
  이미 있는 것처럼 적혀 있다 (실제로는 랩이 M9 이상 정답 구성일 때만 있다)

> 고칠 것 — M9 3.4 의 설정 예시에 `pasv_address` 를 넣거나(그 자리가 자연스럽다),
> M10 3장에 "FTP 서버에 공개 주소를 알려 준다" 를 할 일로 추가한다.

### M10-3 · 어긋남 — 3.1 의 "규칙이 없습니다" 도 사실이 아니다

`sudo nft list ruleset` 이 비어 있어야 한다고 적혀 있는데, [이 모듈 적용] 직후
**전체 방화벽 규칙이 이미 올라와 있다.** `reset.yml` 이 이렇게 되어 있다.

```yaml
- name: 방화벽 규칙 다시 넣기
  ansible.builtin.command: nft -f /etc/nftables.conf
  when: node_role == 'edge' and reset_files.results[1].stat.exists
```

`nft flush ruleset` 으로 지운 뒤, **단계와 상관없이** 남아 있는 파일을 다시 읽는다.
파일은 예전 M10 적용 때 만들어진 것이라 그대로 살아난다.
(앞의 「되돌리기가 한 방향으로만 수렴한다」와 같은 뿌리다.)

## M11 — 트러블슈팅 · 캡스톤

### M11-1 · 막힘 — **아무 장애도 없는 랩이 캡스톤 채점에서 떨어진다**

`m11` 단계를 [이 모듈 적용] 으로 올리고(=기계가 만든 정답 구성), 아무것도 건드리지
않은 채 캡스톤과 같은 검사를 돌렸다.

```
70/72 통과 → 불합격
```

두 개가 **정상인데 실패**한다.

**① `r3 의 링크가 모두 살아 있는가 (백업 경로 라우터)`**

```
출력에 '=' 가 있으면 안 된다 (실제: eth3.10-10=down
                                eth3.20-20=down)
```

이 둘은 r3 의 VRRP 가상 MAC 인터페이스다. **r3 는 BACKUP 이므로 내려가 있는 것이
정상**이다 — M5 3.5 가 그렇게 가르친다.

> **주소는 양쪽 다 붙어 있는데 BACKUP 쪽은 인터페이스가 내려가 있습니다.**

검사는 `ls /sys/class/net | grep -E '^eth'` 로 훑어 전부 `up` 이기를 요구한다.
M5 가 생긴 뒤로 이 검사는 **정상 랩에서 반드시 실패한다.**

**② `M03 · 경로가 설계대로 r1 → r2 → r4 를 지나는가`**

```
expect_all: ['10.10.10.254', '10.10.64.2', '10.10.64.10', '10.10.40.11']
실제 traceroute:
 1  10.10.10.252      ← r1 의 실주소. 가상 IP 가 아니다
 2  10.10.64.2
 3  10.10.64.10
 4  10.10.40.11
```

M5 부터 `10.10.10.254` 는 macvlan 위의 가상 IP 이고, 라우터가 ICMP 오류를 보낼 때
쓰는 출발지는 부모 인터페이스의 실주소(`10.10.10.252`)다. 그래서 첫 홉이 `.254` 로
찍히지 않는다. 이 검사도 **M5 이후로는 통과할 수 없다.**

**무슨 뜻인가** — 캡스톤은 주입된 장애를 다 고쳐도 **최대 70/72** 다.
시간을 다 쓰고 완벽하게 복구한 교육생도 "불합격" 을 본다. 그리고 그 두 줄은
어디를 봐도 고칠 수 없는 것이라, 남은 시간을 거기에 쏟게 된다.

> 고칠 것 —
> ① `r3-links` 는 VRRP 가상 인터페이스(`*-<vrid>`)를 빼고 본다. 그게 곧
>    "BACKUP 은 내려가 있다" 를 검사가 아는 방법이다
> ② `path-as-designed` 의 첫 홉 기대값을 단계에 맞춘다 (M5 이상은 `.252`),
>    또는 첫 홉을 빼고 2·3·4 홉만 본다

### M11-2 · 걸림돌 — 채점표의 퀴즈 문항 수가 다르다

5장 「채점」 표에 `퀴즈 | 방법론 **10문항**` 이라고 적혀 있는데 실제 M11 퀴즈는
**11문항**이다.

```
named    inactive,  /etc/bind/db.lab.local  없음
vsftpd   inactive,  /etc/vsftpd.conf        없음
pc1      /etc/resolv.conf                   없음
```

## 신규 랩에서 M9 · M10 을 다시 열어 봤다

앞의 M09-1 · M10-3 은 "되돌리기로 내려온 랩" 에서 본 것이라, 정말 새로 만든 랩에서도
같은지 확인이 남아 있었다. 그래서 랩을 **통째로 지우고 다시 만들었다.**

```
terraform destroy   27 destroyed
terraform apply     27 added          ← VM 13대가 전부 새것
playbooks/wait.yml  13/13 부팅 확인
```

그 위에서 M9 → M10 을 [이 모듈 적용] 부터 순서대로 열어 3장을 손으로 만들었다.

**M9 는 교재가 정확히 맞았다.** 시작 상태(`/etc/resolv.conf` 없음, `connection refused`,
`named` inactive, 21번 아무도 안 들음)도, 3.2~3.5 의 출력도 그대로다. 3.4 에 넣어 둔
계정 만들기까지 따라가면 `curl -u ftpuser:labpass` 가 파일을 받아 오고 **8/8 통과**다.
되돌리기 수정도 확인됐다 — 서비스도 파일도 하나도 남아 있지 않았다.

**M10 은 그렇지 않았다.** 새 랩에서만 드러나는 것이 둘 나왔다. 아래 FRESH-1 · FRESH-2 다.

### FRESH-1 · 막힘 — 새 랩에서는 **외부 사이트가 꺼져 있다** (M10 · M3)

M10 3.5 는 SNAT 가 걸렸다는 것을 이렇게 증명한다.

```bash
# pc1
curl -sS -o /dev/null -w '%{http_code}\n' http://198.51.100.10/
200
```

새 랩에서 실제로 나온 것 —

```
curl: (7) Failed to connect to 198.51.100.10 port 80 after 3 ms
```

SNAT 는 정상이었다. `edge` 의 바깥쪽에서 잡아 보면 출발지가 제대로 바뀌어 나간다.

```
203.0.113.1.48442 > 198.51.100.10.80: Flags [S]
198.51.100.10.80 > 203.0.113.1.48442: Flags [R.]      ← RST
```

`inet` 에서 **80번을 아무도 듣고 있지 않았다.** `198.51.100.10/32` 는 `lo0` 에 붙어
있는데 nginx 가 안 뜬 것이다. 이 노드는 "남의 사이트" 라 교재 어디에도 올리라는
말이 없다 — 랩이 깔아 줘야 하는 배경이다.

원인은 `roles/server` 의 nginx 조건이 `svc_active`(= `config_stage` ≥ 그 노드의 단계)
라는 것이다. 직접 만드는 단계에서는 [이 모듈 적용] 이 `config_stage` 를 한 칸 낮춰
올리므로, **그 모듈에서 처음 등장하는 노드의 서비스가 자기 단계에 도달하지 못한다.**

| 모듈 | config_stage | 그 노드 | 결과 |
|---|---|---|---|
| M10 | m9 | `inet` (m10) | 외부 사이트가 안 뜬다 |
| M3 | m2 | `web` (m3) | 목적지 웹 서버가 안 뜬다 |

**M3 도 같이 걸린다.** 확인해 봤다 — 옛 조건으로 M3 의 시작 상태를 만들면
`web` 의 nginx 가 `inactive` 이고 `curl http://10.10.40.11/health` 가 아무것도 못 받는다.
M3 교재 3장과 6장이 그 `curl` 로 경로를 증명하고, 검사에도 같은 항목이 있다.

지금까지 안 보였던 이유 — 높은 단계까지 갔던 랩을 되돌리면 nginx 는 내려가지 않아
그대로 살아 있다. **새로 만든 랩에서만** 드러난다.

> 고친 것 — nginx 만 `node_active`(그 단계에 노드가 존재하는가)로 옮겼다.
> 교재 어디에도 nginx 를 올리라는 할 일이 없으므로, 교육생이 만드는 것이 아니라
> 랩이 깔아 주는 배경이라는 사실을 조건에 그대로 적은 것이다.

### FRESH-2 · 막힘 — M10 은 무엇을 해도 8/9 에서 멈춘다 (`pasv_address`)

M10 3장을 교재대로 다 만들고 검증을 돌렸다.

```
8/9 통과 → 불합격
  [FAIL] FTP 서버가 밖에 알려 줄 **공개 주소**를 설정하고 있는가
         출력에 '1' 가 없다 (실제: 0)
```

`ftp` 의 `/etc/vsftpd.conf` 에 `pasv_address` 가 없다. M9 3.4 에서 손으로 써 넣은
줄인데, **M10 에서 [이 모듈 적용] 을 누르는 순간 지워진다.** 템플릿이 그 줄을
`config_stage` ≥ m10 일 때만 넣는데, M10 의 [이 모듈 적용] 이 올리는 것은 m9 이기
때문이다. 그리고 M10 교재는 그 줄을 다시 쓰라는 말을 하지 않는다 — 할 수 있는 일이 없다.

> 고친 것 — 템플릿의 기준을 m9 로 내렸다. M9 3.4 가 교육생에게 쓰게 하는 줄이므로
> M9 를 마친 랩에는 그 줄이 있는 것이 맞다.

고친 뒤 새 랩에서 M10 3장을 처음부터 다시 만들어 **9/9 통과**를 확인했다.

### FRESH-3 · 어긋남 — `dnat-ftp-passive` 는 `pasv_address` 를 보지 않는다

위의 `pasv_address` 가 없는 상태에서도 이 검사는 통과했다.

```
[PASS] 외부 → FTP 공개 IP 로 Passive 전송이 되는가 ★
```

힌트가 "227 응답에 **공개 IP** 가 들어 있는가" 라고 적어 둔 바로 그것을 안 보고 있었다.
요즘 `curl` 은 EPSV 를 먼저 쓰고(응답에 주소가 없다), 7.74 부터는 PASV 응답의 주소도
무시하고 제어 연결의 주소를 재사용하는 것이 기본값이다. 두 옵션을 끄고 확인했다.

```
$ curl --disable-epsv --no-ftp-skip-pasv-ip -u ftpuser:labpass ftp://203.0.113.12/hello.txt
curl: (7) Failed to connect ...          ← pasv_address 없을 때
my-network-lab FTP test file             ← 있을 때
```

이 모듈이 "FTP 가 NAT 를 싫어하는 이유" 를 가르치는데, ★ 가 붙은 검사가 그것을
확인하지 않고 있었다.

> 고친 것 — 검사 명령에 `--disable-epsv --no-ftp-skip-pasv-ip` 를 붙였다.

### FRESH-4 · 어긋남 — `m09-05` 는 주입해도 [검증] 이 8/8 로 통과한다

M9 의 장애 다섯 개를 하나씩 주입하고 검증을 돌려 봤다. 넷은 제대로 걸렸다.
`m09-05`(게이트웨이 주소 중복)만 **주입한 채로 8/8 합격**이 나왔다.

시나리오는 `dns` 에 게이트웨이 주소를 붙이고 `arping -U` 로 알린다. 그런데 리눅스는
기본값에서 **이미 갖고 있는 항목만** 일방적 통보로 갱신하고 없던 항목은 만들지 않는다.
그때 `web` 의 캐시가 비어 있어서, 정작 검사가 보는 노드는 멀쩡했다.

```
web  ip neigh show dev eth1 → (게이트웨이 항목 없음)      ← 아무 일도 안 일어났다
ftp  10.10.40.254 lladdr 52:54:00:43:00:01                ← 여기만 걸렸다
```

가로챈 주소에서 한 번 말을 걸게 해 두 대 다 확실히 배우게 고쳤다. 그러고 다시 보니
이번에는 **몇십 초 뒤에 저절로 낫는다.** 같은 주소에 두 대가 답하므로 캐시가 만료될
때마다 나중에 답한 쪽이 이기고, `r4` 가 이기면 통신이 된다. 계속 알리게 해 두고
90초를 지켜봤다.

```
t=15s  dns   t=30s  r4    t=45s  dns   t=60s  r4    t=75s  r4    t=90s  dns
curl   200          200          000          200          200          200
```

**이 장애는 원래 간헐적이다.** 그래서 [검증] 이 도는 그 순간에는 멀쩡할 수 있어
판정이 성립하지 않는다.

> 고친 것 — ① 주입 즉시 증상이 보이게 하고 [복구] 전까지 계속 알리게 했다
> (한 번만 알리면 저절로 낫는다), ② 시나리오 머리말의 증상을 "전부 안 된다" 에서
> "됐다 안 됐다 한다" 로 바로잡고 교재 5장 증상표도 같이 고쳤다,
> ③ `ungraded_scenarios` 에 넣었다 — `m08-01` · `m10-05` 와 같은 이유다.
> 간헐적 장애는 오히려 좋은 연습거리라 메뉴에는 그대로 둔다.

## 신규 랩에서 M3 · M4 를 다시 열어 봤다

FRESH-1 이 M3 도 걸린다고 적어 두었으니 그것부터 확인해야 했다. 랩을 다시 통째로

**둘 다 교재대로 만들면 통과한다.** M3 **9/9**, M4 **11/11**. 장애 시나리오도
`m03-01`~`m03-04` 넷, `m04-01`~`m04-04` 넷이 전부 검사에 걸리고 [복구] 로 깨끗이 돌아왔다.

**FRESH-1 이 M3 에서도 고쳐진 것을 확인했다.** 새 랩의 M3 시작 상태에서 `web` 의

교재 쪽에서 새로 나온 것은 아래 여덟이다.

### FRESH-6 · 막힘 — 6장의 "되돌리려면 `restart frr`" 가 3장을 지운다 (M3)

M3 6장 머리말과 6.6 이 이렇게 적어 두었다.

```
되돌리려면 sudo systemctl restart frr 가 가장 확실합니다
(설정 파일 기준으로 원복됩니다 — 실습 중에는 write memory 를 하지 말 것)
```

3.0 에서 `write memory` 를 하지 말라고 했으므로, 그 "설정 파일" 에는 **3장에서 적은
넉 줄이 없다.** 실제로 쳐 봤다.

```
restart 전   S>* 10.10.32.0/19 [1/0] via 10.10.64.2, eth2
restart 후   (한 줄도 없음)
pc1 ping     2 packets transmitted, 0 received, 100% packet loss
```

6.2 나 6.6 이 엉켰을 때 그 문장을 그대로 따르면 **이 모듈을 처음부터 다시 만들어야
한다.** 그런데 화면에는 아무 경고도 없고, [검증] 을 돌려야 떨어진 것을 안다.

> 고친 것 — 3.0 에 "뒤집어 말하면 저장하지 않은 것을 전부 지운다" 를 붙이고,
> 6장 머리말은 각 실습의 「정리」를 먼저 쓰라고 바꿨다. 6.6 의 마지막 줄은
> `show ip route static` 으로 3.5 의 넉 줄과 대조하라는 것으로 바꿨다.

### FRESH-7 · 어긋남 — 중간 점검은 "시작 상태" 가 아니라 **다 끝낸 상태**로 맞춘다

M3 과제 6(중간 점검) 안내가 이렇게 적혀 있었다.

```
① 랩이 이 모듈의 시작 상태로 맞춰집니다  (실습 중 만든 설정은 사라집니다)
```

M3 에서 "시작 상태" 는 3.1 의 그것 — 정적 경로가 한 줄도 없는 상태다. 그 말대로라면
중간 점검은 시작하자마자 전부 실패한다. 실제로는 그렇지 않다. 콘솔의 `drill` 은
`gen`(목표 구성)을 쓴다 — 직접 만드는 단계에서도 그렇다. 확인해 봤다.

```
r1  S>* 10.10.32.0/19 via 10.10.64.2      ← 정적이 다 서 있다
r4  S>* 10.10.0.0/19  via 10.10.64.9
pc1 ping → 0% packet loss
```

M7 의 같은 문장도 함께 고쳤다 (M7 은 직접 만드는 단계가 아니라 결과는 같지만,
문장은 한 가지로 맞춰 두는 편이 낫다).

### FRESH-8 · 걸림돌 — 6.6 의 출력 예시가 순서도 표시도 다르다 (M3)

floating static 을 넣은 뒤의 `show ip route 10.10.32.0/19` 예시다.

| | 교재 | 실제 |
|---|---|---|
| 순서 | AD 1(best) 이 먼저 | **AD 200 이 먼저** 나온다 |
| 표시 | 둘 다 `  * ` | 지는 쪽에는 `*` 가 **없다** |

두 번째가 특히 나쁘다. 3.2 에서 "`>` 와 `*` 가 둘 다 붙어 있어야 합니다" 를 배웠는데,
지지 않는 쪽에 `*` 를 붙여 놓으면 그 표시가 무슨 뜻인지 되묻게 된다.

> 고친 것 — 실제 출력으로 바꾸고, `*` 가 없는 것이 무슨 뜻인지 두 줄 붙였다.

### FRESH-9 · 걸림돌 — `show ip route ospf` 는 예시보다 훨씬 길다 (M4)

3.3 의 예시는 한 줄, 3.5 는 세 줄이다. 실제로는 3.3 에서 일곱 줄, 3.5 에서 열한 줄이 나온다.

```
O   10.10.10.0/24 [110/1] is directly connected, eth1.10      ← 발밑 대역
O   10.10.64.0/30 [110/10] is directly connected, eth2        ← 발밑 대역
O>* 10.10.64.8/30 [110/20] via 10.10.64.2, eth2               ← 교재가 보여 준 줄
```

`>*` 가 없는 `O` 줄들이다. OSPF 도 자기 발밑 대역을 알지만 `C` 가 이기므로 안 쓰인다.
교재는 새로 배운 줄만 옮겨 적었는데 그 사실을 밝히지 않아, 화면과 예시가 안 맞는다.

> 고친 것 — 3.3 에 그 `O` 줄들을 예시로 넣고 `>*` 가 없는 이유를 붙였다.
> 3.5 에는 "`>*` 붙은 줄만 옮겼다" 한 줄을 붙였다.

### FRESH-10 · 걸림돌 — 6.2 의 역방향 traceroute 3번 홉 주소가 틀렸다 (M4)

`r1` 의 `eth2` cost 를 200 으로 올린 뒤 `web` 에서 되짚어 본 것이다.

| 홉 | 교재 | 실제 |
|---|---|---|
| 2 | `10.10.64.9` | `10.10.64.9` |
| 3 | `10.10.64.1` (r1 의 eth2) | **`10.10.64.5`** (r1 의 eth3) |

결론("여전히 r2 를 지난다")은 맞다. 틀린 것은 3번 홉의 주소인데, 하필 그 자리가
M3 6.3 에서 "홉에 보이는 주소는 들어온 쪽 인터페이스" 라고 배운 그 지점이다.
여기서는 `r1` 이 답을 **내보내는** 인터페이스가 찍힌다 — cost 를 올려 `r1` 이
`web` 쪽으로 나가는 문이 `eth3` 로 바뀌었기 때문이다.

> 고친 것 — 주소를 실제 값으로 바꾸고, 앞에서 배운 규칙이 **경로가 대칭일 때만**
> 그렇게 보인다는 것을 붙였다. 비대칭을 가르치는 절이라 오히려 좋은 자리다.

### FRESH-11 · 걸림돌 — 수렴 실습의 숫자 두 곳 (M4)

`ping -i 0.05` 로 여러 번 재 봤다.

| 무엇 | 교재 | 실제 |
|---|---|---|
| 6.1 정리 (링크 복구) | "이때도 ping 이 **한두 개 빠집니다**" | `-i 0.05` 에서 0~1 개. `-i 0.2` 로는 거의 안 보인다 |
| 6.4 로그 예시 | `... [eth3]'s MTU 1400` | `Packet[DD]: ... [eth3:10.10.64.5]'s MTU 1400` |

### FRESH-12 · 판단 — 과제 3 의 비교 축을 바꿨다 (M4)

넘겨 둔 항목이다. 세 가지 조작을 `-i 0.05` 로 각각 재 봤다.

```
① r1 eth2 down        0 ~ 1 개
② r2 eth1 down        0 ~ 1 개
③ r1 eth2 cost 200    0 ~ 1 개
```

여섯 번 재서 대부분 0 이고 가끔 1 이다. **잃은 패킷 수로는 셋이 구분되지 않는다.**
표의 첫 비교 축이 그것이었다.

셋을 실제로 가르는 것은 그 순간 장비가 본 것이다.

| | 직후 `show ip ospf neighbor` | 이웃이 사라지기까지 | 감지 계기 |
|---|---|---|---|
| ① | 이웃이 즉시 사라진다 | 즉시 | 내 포트의 carrier 상실 |
| ② | `Full` 인데 Dead Time 만 준다 | 40초 | 상대가 뿌린 새 지도 |
| ③ | 끝까지 `Full` | 안 사라진다 | 장애가 아니다 — 내가 바꿨다 |

> 고친 것 — 표를 이 세 축으로 바꾸고, 패킷 수는 참고 열로 내렸다. 그리고
> "셋 다 사용자 화면에는 표가 안 났는데 그래도 장애인 것은 어느 것인가" 를 물음에 넣었다.
> 숫자를 재는 과제에서 **무엇을 보고 알았는가**를 묻는 과제로 옮긴 것이다.

## 아직 안 한 것

- **M11-1 의 뿌리**는 검사 쪽만 고쳤다. `r3-links` 처럼 "모든 eth 가 up" 을 보는
  검사가 `r2-links` · `r4-links` 에도 있다. 그 둘에는 VRRP 인터페이스가 없어
  지금은 문제가 없지만, 나중에 이중화를 늘리면 같은 자리에서 또 걸린다.
- **남은 모듈의 신규 랩 확인** — M0 · M1 · M2 · M5~M8 · M11 은 신규 랩에서 처음부터
  다시 열어 보지 않았다. 지금까지 새 랩에서만 드러난 것은 전부 "그 모듈에서 처음
  등장하는 노드의 서비스" 였고 그 뿌리는 고쳤으니, 남은 것은 확인 작업이다.
